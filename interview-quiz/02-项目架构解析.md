# 项目架构解析：BookMind 是怎么跑起来的

> 目标：读完后你能在白板上画出一次提问的完整链路，并解释“为什么这样设计”。
>
> 先记住一句话：**BookMind 是一个“教材 + 学习闭环”的 AI 学习助手，前端 Next.js，后端 FastAPI，核心是一个带工具循环的单 Agent。**

---

## 1. 一句话定位

BookMind（学迹）围绕一份教材，把四件事连在同一组知识点上：

```text
读原文 → 定目标 → 做练习 → 记笔记
```

它不是“通用聊天机器人”，而是把 Agent 能力约束在学习场景里：

- 回答必须尽量基于原文
- 引用必须能定位到页/节
- 学习状态不能随便写
- 练习和复习要有证据

**面试一句话**：

> BookMind 是一个教材驱动的 AI 学习助手。它用单 Agent 循环 + 工具调用，把阅读、导学、练习、笔记串成一个有证据链的学习闭环；前端 Next.js，后端 FastAPI，数据用 SQLite 和文件存储。

---

## 2. 技术栈与运行形态

| 层 | 技术 | 说明 |
| --- | --- | --- |
| 前端 | Next.js 16、React 19、TypeScript | 页面、流式对话、PDF/Markdown 阅读器、图解 |
| 后端 | FastAPI、Uvicorn、WebSocket | HTTP API + 流式事件 |
| Agent | 自研 `AgentLoop` + capability 插件 | 单轮多轮工具调用 |
| 模型 | OpenAI 兼容 API（DeepSeek/OpenAI/Claude 等） | 文字模型，可选视觉模型 |
| 检索 | 定位全文检索 + LlamaIndex/FAISS/BM25 | 阅读与知识库走不同路径 |
| 存储 | SQLite + 文件 | 会话、学习状态、教材、笔记 |
| 打包 | setuptools（`pip install -e .`） | Python 包 + CLI |

运行端口：

- 前端：`http://127.0.0.1:8018`
- 后端：`http://127.0.0.1:8019`
- 健康检查：`GET /health/ready`

**面试一句话**：

> 前后端分离但同机部署：Next.js 负责交互和阅读体验，FastAPI 负责接口、流式通信和学习引擎；模型通过 OpenAI 兼容协议接入，不绑定某一家。

**记忆方法**：

- `textbook` 是“关系层”：谁和谁属于同一本教材
- `reading` 是“原文层”：内容在哪、怎么定位

- `agents` 是“执行层”：模型怎么想、怎么调工具
- `capabilities` 是“能力层”：这次对话允许做什么

## 4. 四个页面与共享数据模型

一个教材有四组稳定 ID：

```text
material_id   阅读资料
workspace_id  阅读工作区
path_id       学习路径
notebook_id   笔记本
```

四个页面各自保存自己的状态，但共享同一组教材、知识点和证据。

| 页面 | 自己负责 | 共享什么 |
| --- | --- | --- |
| 自主学习 | 阅读位置、标注、阅读对话 | 教材、知识点、来源、笔记 |
| AI 导学 | 当前导学位置、导学对话 | 知识点、评估证据、掌握记录 |
| 练习巩固 | 出题配置、题组、练习对话 | 原文范围、作答记录、错题、复习状态 |
| 学习笔记 | 笔记内容、引用关系 | 教材位置、相关知识点 |

**为什么这样设计**：

- 阅读对话、导学对话、练习对话互相隔离，避免上下文串味
- 但学习证据是共享的，练习答错会影响掌握度和复习计划
- 所有内容都挂 stable ID，改名/换存储不会断引用

**面试一句话**：

> 四个页面不是四个孤立功能，而是共享同一套教材和知识点 ID；每个页面只拥有自己的交互状态，学习证据统一沉淀，所以“读—学—练—记”能闭环。

## 5. 一次提问的完整链路（阅读模式）

这是面试最值得讲清楚的流程。

```text
1. 用户在阅读页选中文本/输入问题
        ↓
2. 前端提交：消息 + material_id + workspace_id + 当前 locator + 模式
        ↓
3. 后端验证会话归属、教材权限，整理上下文
        ↓
4. ReadingCapability 激活：
   - 系统提示词注入“当前打开哪份资料、看到第几页、怎么引用”
   - pre_loop 用确定性全文搜索定位问题
   - 把 top 4 命中作为 seed 注入本轮用户消息（不调用 LLM）
        ↓
5. AgentLoop 开始：
   - 调模型
   - 模型可能调用 material_outline / search_material / read_material
   - 工具在服务端执行，material_id 由服务端注入
   - 工具结果作为 role=tool 消息回到对话
   - 模型继续，直到某一轮不再调用工具
        ↓
6. 模型输出答案 + 引用；前端流式显示
        ↓
7. 如果模型调用 reader_goto：
   - 校验 quote 是否真的在该 locator
   - 校验通过才高亮/跳转
        ↓
8. 后端保存会话、事件、引用；前端更新阅读位置
```

对应代码：

- `bookmind/capabilities/reading/capability.py`：激活、提示词、pre_loop、参数注入
- `bookmind/capabilities/reading/tools.py`：8 个阅读工具
- `bookmind/reading/search.py`：三层定位搜索
- `bookmind/agents/loop/agent_loop.py`：循环
- `bookmind/agents/loop/pipeline.py`：工具组合、消息构建、dispatch

**面试一句话**：

> 阅读模式下，系统先在本地做一次确定性定位检索，把“问题可能在第 12 页和第 17 页”直接交给模型，再让模型按需读原文、给引用、驱动页面跳转。整个过程不需要 embedding，也不需要向量库。

## 6. Agent Loop：这个项目的“智能体”到底在哪

核心文件：`bookmind/agents/loop/agent_loop.py`。

规则非常简单：

```text
一次用户提问 = 一个不断增长的对话
每一轮 = 一次 LLM 调用

这一轮调用了工具？
  → 留住模型的旁白 + tool_calls
  → 执行工具，把结果作为 role=tool 追加
  → 继续下一轮

这一轮没有调用工具？
  → 这就是最终回答
  → 结束
```

几个产品化细节：

| 机制 | 作用 |
| --- | --- |
| `DEFAULT_MAX_ROUNDS = 8` | 控制探索预算，防止死循环 |
| `MAX_SETTLEMENT_ROUNDS = 3` | 预算用完后，给已开始的交互留收尾空间 |
| 最后一轮强制无工具 | 防止模型永远停不下来 |
| `MAX_PARALLEL_TOOL_CALLS = 15` | 同一轮工具并行执行的上限 |
| `ask_user` | 暂停循环，等用户回答后继续 |
| 上下文 90% 守卫 | 超限前压缩/裁剪 |
| 流式事件 | 文字、工具调用、引用、图解边生成边推送 |

**为什么说它是 Agent，而不是普通聊天**：

- 模型能决定调用哪个工具
- 工具结果会改变下一步
- 有循环和终止条件
- 有预算和失败恢复
- 工具参数由服务端注入，模型不能越权

**面试一句话**：

> 它的 Agent 性体现在“模型在循环里根据工具结果决定下一步”，而不是“用了多智能体框架”。单 Agent + 能力插件，比多 Agent 更容易控制成本和调试。

## 7. Capability：能力插件

Capability 是“这次对话允许模型做什么”的插件。它可以在几个时机介入：

| 钩子 | 作用 | 例子 |
| --- | --- | --- |
| `is_active` | 这次是否激活 | 有打开教材就激活阅读能力 |
| `system_block` | 注入系统提示 | 告诉模型当前资料、页码、引用规则 |
| `owned_tools` | 增加工具 | `search_material`、`read_material` |
| `augment_kwargs` | 服务端注入参数 | 注入 `material_id`，模型不能自己填 |
| `pre_loop_seed` | 同步低成本预检索 | 当前视口、选中文本 |
| `pre_loop` | 异步预处理 | 对用户问题做本地定位搜索 |

**设计价值**：

- 能力可插拔，不用改 Agent 主循环
- 权限边界清晰：模型看不到没打开的教材 ID
- 不同学习模式共享同一套循环，只换提示词和工具

**面试一句话**：

> Capability 把“场景规则”从 Agent 主循环里拆出来：阅读、导学、解题各自声明自己何时激活、注入什么提示、拥有哪些工具，主循环保持通用。

## 8. 阅读检索：为什么不用向量库

这是项目最有辨识度的设计，也是面试高频追问点。

### 做法

`bookmind/reading/search.py` 对当前教材的所有单元做线性扫描，三层匹配：

1. **exact**：原文精确匹配（忽略大小写）
2. **normalised**：空白折叠、标点弱化，适配 PDF 换行/中英文标点
3. **terms**：按查询词命中数量排序；中文长串拆成重叠 bigram

每个命中都天然带 `locator`（页码/章节/幻灯片/小节号）。

### 为什么

- 一份教材通常只有几百个单元，线性扫描是毫秒级
- 每个命中已经带定位，模型可以直接引用“第 12 页”
- 向量检索返回的是“语义相近的块”，定位信息是后补的，容易引用错
- 阅读场景的问题是“这句话在哪”，不是“意思相近的内容有哪些”

### 代价

- 不懂同义词和改写
- 依赖原文措辞
- 中文需要 bigram 兜底
- 教材特别大时线性扫描会变慢（但仍在可控范围）

### 什么时候该用向量

- 资料量很大（数万篇）
- 问题与原文措辞差异大
- 跨语言、跨文档语义检索
- 需要“相似案例/相关概念”而不是“精确出处”

**面试一句话**：

> 阅读场景的核心需求是“可定位的证据”，不是“语义相似”。几百个单元的线性扫描足够快，而且每个命中天然带页码，所以这里用 locator 全文检索比向量库更合适；向量检索保留在知识库和大规模资料场景。

## 9. RAG 在项目里的真实位置

不要把所有检索都叫 RAG。BookMind 里有三条不同的路径：

### 路径 A：阅读模式（默认）

```text
原文单元 → 线性全文扫描 → locator + snippet → 模型读原文 → 回答 + 引用
```

- 不需要 embedding
- 不需要向量库
- 核心是定位和引用

### 路径 B：知识库 / LlamaIndex

```text
文档 → 解析 → chunk（默认 512 / overlap 50）
     → embedding → FAISS 向量索引
     → BM25 关键词索引
     → 混合检索（RRF 融合）
     → 可选 cross-encoder rerank
     → 拼进 Prompt
```

代码：

- `services/rag/pipelines/llamaindex/pipeline.py`
- `.../retrievers.py`：向量 + BM25 + `QueryFusionRetriever`
- `.../config.py`：`hybrid` 默认，BM25 缺失时降级为 vector
- `.../rerank.py`：可选精排

### 路径 C：PageIndex

PageIndex 的思路是“用推理做检索”：不靠向量近邻，而是让模型根据目录/结构推理该读哪一部分。项目保留了适配器，但当前主学习流程不依赖它。

### AI 导学用哪条

`learning/lesson_evidence.py` 在准备小节时：

1. 让模型生成最多 3 条检索 query
2. 对选中的资料索引做检索（可能是 vector/hybrid，也可能是 legacy page BM25）
3. 把命中的原文页作为证据，再规划学习目标

**面试一句话**：

> 这个项目不是“所有地方都 RAG”。阅读模式用定位全文检索，知识库用 LlamaIndex 向量/BM25 混合检索，PageIndex 作为结构化推理检索的适配器保留。选哪种，取决于场景要的是“可定位出处”还是“大规模语义召回”。

## 10. 学习闭环：目标、证据、练习、复习

### 学习目标

`textbook/planning.py` 把一个小节拆成 1-6 个目标，每个目标有：

- 名称
- 类型：记忆 / 概念理解 / 步骤技能 / 设计判断
- 可检查的掌握要求
- 原文 locator 来源

不是“四级难度”，而是不同认知类型。

### 证据

- 阅读：读过哪些 locator、标注了什么
- 导学：解释、追问、随堂测验
- 练习：作答、判分、错题
- 笔记：自己的总结与引用

证据写入学习状态前要经过范围校验，未验证内容不能改掌握度。

### 练习

- 选择题、填空题、简答、编程等
- 客观题程序判分，主观题模型评阅
- 错题进入错题本
- 复习队列按遗忘风险排序

### 复习

`learning/scheduler.py` 是“指数遗忘 + 类型冷启动先验”的调度器，**不是校准过的 FSRS**。这一点面试时要说准确，别夸大。

**面试一句话**：

> 学习闭环的关键不是“生成题目”，而是“证据能写回状态”：每个目标有来源，每次作答有记录，错题进入复习队列，掌握度由证据驱动而不是模型随口判断。

## 11. 存储与一致性

- SQLite：会话、教材关联、学习状态、练习记录
- 文件：原文单元、索引、标注、笔记、生成资料
- `data/user/` 是运行数据根目录，`BOOKMIND_HOME` 可改
- 教材删除是“可恢复移除”：`removed_at` 标记，不物理删原文/会话/笔记
- 多存储之间靠稳定 ID + 进程锁 + 幂等恢复连接

**面试一句话**：

> 这个项目没有上分布式数据库，而是 SQLite + 文件 + 稳定 ID。单机场景下简单可靠；代价是跨存储一致性要靠应用层保证，多进程并发写入需要额外协调。

## 12. 设计取舍（面试重点）

### 取舍 1：locator 全文检索 vs 向量检索

- 选 locator：可定位、可引用、快、无需 embedding
- 放弃：语义泛化、同义改写
- 适用：单份教材、强调出处

### 取舍 2：单 Agent vs 多 Agent

- 选单 Agent + capability：成本低、调试简单、上下文统一
- 放弃：复杂任务的专业分工
- 适用：学习场景边界清晰

### 取舍 3：SQLite + 文件 vs 分布式存储

- 选轻量：本地部署、零运维、数据可控
- 放弃：多进程/多机扩展
- 适用：个人/小团队本地应用

### 取舍 4：Prompt 约束 vs 代码护栏

- 两者都用，但关键边界写成代码
- 例：quote 校验、material_id 注入、会话隔离、写入范围校验

### 取舍 5：生成 vs 检索

- 能检索到原文时优先原文
- 生成用于解释、举例、出题、总结
- 教材外知识要明确标注，不能伪装成教材依据

**面试一句话**：

> 这个项目最重要的取舍是“可靠性优先于炫技”：阅读场景用可定位的全文检索，Agent 用单循环加预算，关键边界写成代码而不是只写 Prompt。

## 14. 项目局限（面试时主动说，反而加分）

- 单机 SQLite，多进程并发写入需要额外协调
- 阅读全文检索不懂同义词，中文依赖 bigram 兜底
- 复习调度不是校准过的 FSRS
- 前端仍保留部分未显示的上游页面/组件
- 依赖较宽，安装体积大，可按阅读/生成/检索拆分
- 多智能体不是默认架构，复杂任务分工有限
- 评估体系有测试和引用校验，但缺少大规模线上指标

**面试一句话**：

> 它不是一个“什么都能做”的通用 Agent，而是一个边界清晰的学习产品；局限主要在单机存储、检索语义泛化和复习模型校准，这些也是下一步最值得做的方向。

---

## 15. 10 个可以主动讲的点

1. 为什么阅读场景不用向量库：定位比语义更重要
2. pre_loop 确定性检索：不花 token、不增加首字延迟
3. material_id 服务端注入：模型不能读没打开的文档
4. quote 校验：引用不真实就不高亮
5. Agent Loop 的预算：8 轮探索 + 3 轮结算 + 强制收尾
6. 工具并行：单轮最多 15 个，带子 trace
7. Capability 插件：场景规则不污染主循环
8. 混合检索：向量 + BM25 + RRF，BM25 缺失自动降级
9. 学习证据：未验证内容不能写掌握度
10. 取舍意识：单 Agent、SQLite、本地优先，都是为可控性服务
