## 一、90 秒项目讲稿

> BookMind 是一个教材驱动的 AI 学习助手。用户导入一份教材后，可以在同一组知识点上完成阅读、目标导学、练习和笔记。
>
> 技术上，前端是 Next.js 16，后端是 FastAPI，核心是一个单 Agent 循环：模型每一轮可以调用阅读、出题、笔记等工具，工具结果再回到对话，直到它不再调用工具。这个循环有轮数、token、超时和上下文预算，还支持 `ask_user` 暂停等用户回答。
>
> 这个项目最有意思的设计是：阅读场景没有直接上向量库，而是用带 locator 的全文检索。因为学习场景更关心“这句话在哪一页”，而不是“语义相似”。每个检索命中天然带页码，模型可以直接引用；跳转和高亮前还会校验 quote 是否真的存在。向量检索、BM25 和混合检索保留在知识库和大规模资料场景。
>
> 我的收获主要是：Agent 产品化的难点不是调模型，而是工具边界、上下文预算、证据校验和失败恢复。这个项目用单 Agent + capability 插件，把复杂度控制在可调试的范围内。

**练习方法**：先照着读 3 遍，再只看关键词复述 3 遍，最后录音 90 秒。

关键词：

```text
教材驱动 / Next.js + FastAPI / 单 Agent 循环 / 工具调用 /
locator 全文检索 / 引用校验 / 向量+BM25 留给知识库 / 预算与边界
```

## 二、项目与架构

### Q1：用一句话介绍这个项目

**面试版**：

> 它是一个围绕教材的 AI 学习助手，把阅读、导学、练习、笔记串成一个有证据链的学习闭环；技术上是一个 FastAPI + Next.js 的单 Agent 应用。

**追问准备**：

- 不是通用聊天机器人：回答受教材和知识点约束
- 不是多智能体：单循环 + capability 插件
- 不是纯 RAG：阅读用定位检索，知识库才用向量/BM25

---

### Q2：为什么前端用 Next.js，后端用 FastAPI？

**面试版**：

> 前端需要复杂的阅读器、PDF/Markdown 渲染、流式对话和状态管理，Next.js + React 的组件生态更合适；后端需要异步 IO、流式接口、模型调用和 Python 的文档处理生态，FastAPI 更顺手。两边通过 HTTP + WebSocket 流式事件解耦。

**追问准备**：

- 同机部署，前端 8018，后端 8019
- CORS 白名单按端口配置
- Python 侧有 PyMuPDF、python-docx、LlamaIndex 等文档/检索生态

---

### Q3：四个页面怎么共享数据，又怎么隔离？

**面试版**：

> 一个教材有稳定的 `material_id`、`workspace_id`、`path_id`、`notebook_id`。四个页面共享这些 ID 和同一套学习证据，但各自保存自己的交互状态和对话。比如阅读对话、导学对话、练习对话是分开的，避免上下文串味；但练习答错会写进同一份掌握度和复习队列。

**追问准备**：

- `textbook/session_scope.py` 防止不同学习会话串用
- 教材删除是可恢复移除，不物理删原文/会话/笔记
- 改名/换存储不会断引用，因为 ID 稳定

---

### Q4：为什么用 SQLite + 文件，不上分布式存储？

**面试版**：

> 这是本地优先的单机应用，数据量和个人使用场景用 SQLite + 文件足够，零运维、部署简单、数据可控。代价是跨存储一致性要靠应用层保证，多进程并发写入需要额外协调；如果要做多人协作或多机部署，就要引入数据库级锁或服务化存储。

**追问准备**：

- SQLite 存会话、教材关联、学习状态、练习记录
- 文件存原文单元、索引、标注、笔记
- 稳定 ID + 进程锁 + 幂等恢复连接多个存储

---

### Q5：这个项目最大的技术难点是什么？

**面试版**：

> 不是调模型，而是“让模型的回答可控”。具体有三件事：第一，工具边界，模型不能读没打开的文档，参数要在服务端注入；第二，上下文和轮数预算，否则成本和延迟失控；第三，证据校验，模型说“第 12 页写了”不算数，要能验证 quote 真的存在。

**追问准备**：

- 这三点分别对应 `augment_kwargs`、`AgentLoop` 预算、`verify_quote`
- 都能落到代码，不是空话

---

## 三、RAG 与检索

### Q6：什么是 RAG？

**面试版**：

> RAG 是检索增强生成：先从资料里检索相关片段，再把片段放进提示词，让模型带着证据回答。它主要解决模型知识过时、没有私有资料、回答不可追溯的问题。RAG 不等于向量数据库，向量检索只是其中一种检索方式。

**追问准备**：

- 流程：解析 → 切块 → 建索引 → 检索 → 重排 → 生成 → 引用
- 它降低幻觉，但不能消除；检索错了，模型会被带偏

---

### Q7：完整讲一下 RAG 的流程

**面试版**：

> 离线阶段：文档解析、清洗、切块，用 embedding 模型把块变成向量，写入向量索引；同时可以建 BM25 关键词索引。在线阶段：用户问题先检索 top-k 候选，必要时用 cross-encoder 重排，把最相关的几段拼进提示词，让模型生成答案并引用来源。最后用 recall、faithfulness、引用准确率去评估。

**追问准备**：

- chunk 默认 512、overlap 50（项目里的 LlamaIndex 配置）
- 混合检索用 RRF 融合
- 可选 rerank，默认关闭

---

### Q8：为什么阅读场景不用向量库？

**面试版**：

> 阅读场景的核心需求是“这句话在哪一页”，不是“语义相近的内容有哪些”。一份教材通常只有几百个单元，线性扫描是毫秒级；每个命中天然带 locator，模型可以直接引用。向量检索返回的是语义相近的块，定位是后补的，反而容易引用错。所以这里用 locator 全文检索更合适。

**追问准备**：

- 三层匹配：exact → normalised → terms
- 中文用重叠 bigram 兜底
- 代价：不懂同义词、依赖原文措辞

---

### Q9：那什么时候该用向量检索？

**面试版**：

> 资料量大、问题与原文措辞差异大、需要跨语言或跨文档语义召回时，向量检索更合适。比如知识库问答、相似案例推荐、海量文档搜索。判断标准是：你要的是“精确出处”，还是“语义相关”。

**追问准备**：

- 精确名称、代码、错误码：BM25 往往更强
- 同义改写、自然语言问题：向量更强
- 两者失败模式不同，可以混合

---

### Q10：BM25 的原理是什么？

**面试版**：

> BM25 是关键词检索的经典打分函数。它看三件事：查询词在文档里出现多少次（TF）、这个词在整个语料里有多稀有（IDF）、文档有多长（长度归一化）。TF 越高越相关，但增长会饱和；IDF 越高说明词越有区分度；长文档要惩罚，避免天然占便宜。

**追问准备**：

- 公式不用背全，讲清 TF、IDF、长度归一化即可
- 中文要分词，分词错误会直接影响效果
- 优点是精确、可解释、无需 GPU；缺点是不懂同义词

---

### Q11：BM25 和向量检索有什么区别？

**面试版**：

> BM25 看“词有没有出现”，向量检索看“语义坐标近不近”。BM25 对专有名词、代码、精确短语很稳，但不懂改写；向量检索擅长同义表达，但可能漏掉精确名称。所以工业界常用混合检索，让两路召回互补。

**追问准备**：

| 维度 | BM25 | 向量 |
| --- | --- | --- |
| 匹配 | 词面 | 语义 |
| 优点 | 精确、可解释、便宜 | 泛化、跨措辞 |
| 缺点 | 怕同义词/分词 | 怕精确名称、需 embedding |
| 典型场景 | 代码、人名、错误码 | 自然语言问答 |

---

### Q12：混合检索怎么融合两路结果？

**面试版**：

> 常见做法是分别召回，再用 RRF 或加权分数融合。RRF 只看排名，不看原始分数，因为向量分数和 BM25 分数尺度不同，直接相加没有意义。项目里用 LlamaIndex 的 `QueryFusionRetriever`，默认 RRF；BM25 依赖缺失时会自动降级为纯向量。

**追问准备**：

- RRF 公式：`Σ 1/(k + rank)`
- 也可以先各自取候选，再统一 rerank
- 代价：复杂度、延迟、调参

---

### Q13：Rerank 的作用是什么？

**面试版**：

> 检索器先粗筛一批候选，rerank 再用更贵的模型精排。常见是 cross-encoder，把“问题 + 文档”一起输入，直接输出相关性分数，比向量点积更准，但慢很多，所以只对前 20 到 100 条做。项目里 rerank 是可选的，配置模型才启用。

**追问准备**：

- 没有 rerank 时，检索器 top-k 就是最终结果
- rerank 用延迟换准确率
- 要监控候选召回，别让好文档在第一阶段就被丢掉

---

### Q14：Chunk 大小怎么定？

**面试版**：

> 没有统一答案，要看文档结构和问题类型。块太大，噪音多、检索不精准；块太小，语义不完整、上下文断裂。项目默认 512 字符、重叠 50，是一个通用起点。更好的做法是按标题/段落做结构切分，再用评估集调参。

**追问准备**：

- overlap 是为了避免一句话被切断
- 代码/表格适合按结构切
- 换 chunk 策略通常要重建索引

---

### Q15：换 embedding 模型要注意什么？

**面试版**：

> 必须重建索引，因为不同模型产出的向量空间不可比。项目里会记录 embedding 配置的签名，索引版本和模型绑定，避免“旧向量用新模型查”。另外要统一归一化方式、维度、距离度量。

**追问准备**：

- `embedding_signature.py`、`index_versioning.py`
- 换模型后要重新评估 recall
- 同一个知识库不要混用多个 embedding 模型

---

### Q16：怎么评估 RAG 效果？

**面试版**：

> 分三层：检索层看 Recall@K，正确答案有没有被召回；生成层看 Faithfulness，回答是否被证据支持；产品层看引用准确率、用户是否真的学会。项目里还有引用存在性校验和测试集，但缺少大规模线上指标，这是可以继续补的。

**追问准备**：

- 构建 golden set：问题 + 标准答案 + 证据页
- 人工评估 + 自动指标结合
- 不要只看“回答像不像”，要看“依据对不对”

---

### Q17：怎么防止模型编造引用？

**面试版**：

> 三个层次：第一，工具返回的片段天然带 locator；第二，提示词要求引用格式；第三，关键动作做程序校验。比如 `reader_goto` 会检查 quote 是否真的出现在该 locator，不匹配就不高亮；保存标注更严格，quote 不存在直接拒绝。未验证的浏览器文本也不会写入学习状态。

**追问准备**：

- Prompt 约束会被绕过，代码校验不会
- 引用错误比“不引用”更伤信任
- 允许模型说“资料中没有”

---

## 四、Agent

### Q18：Agent 和工作流有什么区别？

**面试版**：

> 工作流是预先写死的步骤，模型只负责其中某些节点；Agent 是模型在循环里根据观察决定下一步，能选择工具、调整计划。Agent 更灵活，但更难控制成本和调试。很多产品其实是“工作流 + 少量模型决策”，这并不丢人，反而更可控。

**追问准备**：

- 这个项目是单 Agent 循环，不是固定工作流
- 但能力边界、工具集合、预算都是工程约束
- 不要为了“Agent”而 Agent

---

### Q19：这个项目的 Agent 循环怎么跑？

**面试版**：

> 一次用户提问就是一个不断增长的对话。每一轮调用一次模型；如果模型调用了工具，就执行工具，把结果作为 `role=tool` 消息追加，继续下一轮；如果这一轮没有工具调用，就是最终回答，循环结束。默认最多 8 轮探索，预算用完还有 3 轮结算，最后强制一次无工具收尾。

**追问准备**：

- 工具并行，单轮最多 15 个
- `ask_user` 可以暂停等用户回答
- 上下文用到 90% 会压缩/裁剪
- 每一轮的文字都会流式显示，工具调用有子 trace

---

### Q20：工具调用怎么保证安全？

**面试版**：

> 模型只负责“提议调用哪个工具、参数是什么”，真正执行在后端。后端会做参数校验、权限校验，并注入模型不该自己填的上下文。比如阅读工具的 `material_id` 由服务端注入，模型不能读取用户没打开的文档；工具还有 guard，失败会返回结构化错误，不会让异常直接冒到用户。

**追问准备**：

- `augment_kwargs` 注入 `material_id` / `workspace_id`
- 会话归属和教材权限在进入循环前验证
- 工具结果作为数据，不执行其中的指令（防提示词注入）

---

### Q21：模型不调用工具怎么办？

**面试版**：

> 两个办法：一是在 pre_loop 里做确定性预检索，直接把“问题可能在第 12 页”放进上下文，弱模型即使不调用工具也能拿到依据；二是在提示词和工具描述里明确“先查目录/先读原文”，并对不合规的输出做重试或修复。项目里阅读能力就是 pre_loop + 工具双保险。

**追问准备**：

- pre_loop 不调用 LLM，不花 token，不增加首字延迟
- 工具描述写清楚“什么时候必须用”
- 对模型输出做协议校验，不合规就修复重试

---

### Q22：工具调用失败怎么办？

**面试版**：

> 工具失败会返回结构化的 `role=tool` 错误，告诉模型“哪个工具、为什么失败”，让模型决定重试、换工具还是向用户解释。后端还有超时、重试、降级和子 trace，避免一个工具卡死整个回合。

**追问准备**：

- 错误信息要包含原因，不能只说“unknown error”
- 并行工具之间互不影响
- 失败要可观测：trace、日志、事件

---

### Q23：上下文超限怎么办？

**面试版**：

> 先做预算：系统提示词、历史、检索结果、工具输出分别占多少。超限时按优先级裁剪：保留系统规则和当前问题，压缩历史，限制检索条数和单条长度，工具输出做摘要。项目里阅读定位只注入 4 条命中、每条 260 字符，就是主动控制上下文。

**追问准备**：

- 上下文窗口不等于记忆
- 压缩会丢信息，要保留关键状态
- 可以用摘要 + 结构化状态代替全文历史

---

### Q24：怎么防止 Agent 死循环？

**面试版**：

> 三道闸：最大探索轮数、结算轮数、最后强制无工具收尾；再加 token 预算、流式空闲超时和工具超时。模型如果一直只推理不行动，还会有 reasoning-only 恢复策略。核心原则是：循环必须有可证明的终止条件。

**追问准备**：

- `DEFAULT_MAX_ROUNDS = 8`
- `MAX_SETTLEMENT_ROUNDS = 3`
- 90 秒流空闲超时
- 强制收尾不是“再试一次”，而是明确结束

---

### Q25：为什么不用多智能体？

**面试版**：

> 这个项目的任务边界比较清晰，单 Agent + capability 插件已经能覆盖阅读、导学、练习等场景，而且上下文统一、成本低、好调试。多智能体会带来通信成本、状态一致性和错误传播问题，不是默认更优。等任务真的需要专业分工时再拆。

**追问准备**：

- 多 Agent 适合：复杂研究、长流程、需要并行专家
- 单 Agent 适合：边界清晰、工具可控、上下文共享
- 架构选择要看任务，不看热度

---

### Q26：MCP 是什么？这个项目用了吗？

**面试版**：

> MCP 是 Model Context Protocol，一套让 Agent 连接外部工具和数据源的标准协议，可以理解为工具侧的 USB 接口。项目依赖里有 MCP，也支持挂载 MCP 工具，但核心不是 MCP 示范项目；主要能力还是内置工具 + capability。

**追问准备**：

- 解决工具接入碎片化
- 标准化工具、资源、提示词
- 不等于新模型能力，主要是互操作

---

## 五、工程与反思

### Q27：流式输出怎么实现？

**面试版**：

> 后端通过 WebSocket/流式事件把模型生成的文字、工具调用、引用、图解推给前端；前端按事件类型增量渲染。工具调用有独立的子 trace，所以用户能看到“正在查资料/正在出题”，而不是干等。

**追问准备**：

- 首字延迟是体验关键
- 半成品状态要能处理
- 断线重连和事件顺序要考虑

---

### Q28：多用户和权限怎么做？

**面试版**：

> 会话和教材都有归属校验，进入循环前验证用户能不能访问这份资料；工具参数在服务端注入，模型不能自己指定没权限的 ID；学习状态的写入也要经过范围校验。单机模式下可以关闭认证，但代码保留了权限边界。

**追问准备**：

- `require_auth` / `require_learning_surface`
- `learning_material_allowed`
- 会话归属校验
- 不要把权限只写在 Prompt 里

---

### Q29：如果让你重做，你会改什么？

## 六、不会的时候怎么答

遇到完全不会的问题，用三步：

1. **承认边界**：“这个概念我没有直接做过，但我理解它大概解决什么问题。”
2. **说出已知**：用你会的相邻概念搭桥。
3. **给出验证方案**：“如果让我做，我会先查 X、做一个小实验验证 Y，再决定。”

示例：

> “FSRS 我没有实际校准过。我知道它是基于记忆稳定性和难度的间隔重复模型；这个项目用的是指数遗忘加类型先验的启发式调度，不是校准过的 FSRS。如果要做，我会先收集作答数据，再用离线评估比较不同调度策略的复习收益。”

## 八、三个 STAR 故事（按真实参与调整）

### 故事 1：模型引用不存在的原文

- **S**：阅读场景要求回答带页码，但模型可能编造 quote。
- **T**：要让“引用”可信，不能只靠提示词。
- **A**：工具返回的片段带 locator；跳转/高亮前校验 quote 是否真的出现在该 locator；保存标注更严格，不匹配直接拒绝；未验证文本不写学习状态。
- **R**：错误引用不会点亮，用户不会被带到错误位置；引用可信度提升。
- **反思**：可靠性要写成代码，不能只写 Prompt。

### 故事 2：阅读场景的检索选型

- **S**：教材问答需要出处，普通向量检索返回的块定位是后补的。
- **T**：在“语义召回”和“可定位证据”之间取舍。
- **A**：选择 locator 全文检索，三层匹配；几百个单元线性扫描足够快；每个命中天然带页码；向量/BM25 留给知识库。
- **R**：回答可引用、可跳转、无需 embedding；代价是不懂同义词。
- **反思**：检索方式要服从场景，不是越先进越好。

### 故事 3：Agent 循环失控

- **S**：工具调用型 Agent 可能一直调用工具，成本和延迟不可控。
- **T**：要有可证明的终止条件和失败恢复。
- **A**：8 轮探索 + 3 轮结算 + 强制无工具收尾；token/超时预算；`ask_user` 暂停；工具并行但限 15 个。
- **R**：循环可终止、可观测、可恢复。
- **反思**：Agent 产品化的核心是编排和边界，不是模型本身。
